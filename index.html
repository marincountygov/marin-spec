Prepare

Gather what you have about the project. Keep the files on your computer. You upload them to your AI tool in the next step.

Gather these

An interview transcript is enough to start. The more you add, the better the spec.

  • Interview transcript
  • Project notes
  • Existing forms
  • Screenshots
  • Process documents
  • Policies
  • Spreadsheets or data
  • Existing requirements
  • Technical documentation
  • Related websites or links
  • Existing code or GitHub repositories

Reduce personal information first

Your files may name residents or staff. Take out what the project does not need.

  • Replace names with roles, such as "Resident A" or "Staff member 1".
  • Take out emails, phone numbers, addresses, and ID numbers.
  • Clean spreadsheets with Marin Anonymizer. Edit transcripts and documents by hand.
  • If the project needs real records, use only the AI tool your department has approved for that information.

This lowers the risk. It does not remove it. You are still responsible for what you upload.

Interview your project owner

Ask these questions in a conversation.

  • Use roles, not names.
  • Skip any that are already answered.
  • Record the conversation and save the transcript.

Project

  • What are we trying to build?
  • What problem are we trying to solve?
  • Why does this matter now?
  • Who owns the project?
  • Who will look after it once it is live?
  • Who should test it before it goes live?

Users

  • Who will use this?
  • What are they trying to do?
  • What problems do they face today?
  • Is this for County staff, the public, or both?

Current experience

  • How does this work today?
  • What works well?
  • What causes problems?
  • What tools or systems are involved?

Future experience

  • What should someone be able to do?
  • What should be easier?
  • What should happen from start to finish?

Content and data

  • What information does the project need?
  • Where does the information come from?
  • Who keeps it up to date?
  • Is any of it private or sensitive?
  • Will the project handle personal information about residents or staff?

Technology

  • What systems must this connect to?
  • Are there existing websites, applications, APIs, or repositories involved?

Access

  • Who can see the information?
  • Who can create or change information?
  • Are there different roles?

Constraints

  • Are there policies, laws, deadlines, technology limits, or other requirements we need to know about?

Success

  • What would make this project successful?
  • How will we know it works?

Before you finish

  • Is there anything we did not ask that we should have?
  • Who else should we talk to?
  • Which documents or examples can you share?

What you get

  • An interview transcript
  • A folder of project files

You're ready when

  • You have a transcript and the files you want to use.
  • You have reduced personal information in them.

Analyze

Your AI tool reads everything and sorts what it finds. It does not write the spec yet.

What you do

  1. Open your AI tool (Claude, ChatGPT, or Copilot) and start a new conversation.
  2. Upload the interview transcript.
  3. Upload your supporting project files.
  4. Copy the analysis prompt, paste it into the message box, and send it.
  5. Wait for the reply. Read it. If something is wrong, tell the tool in a new message.

Stuck? See If something goes wrong in About.

Analysis prompt

Paste this after you upload your files.

You are helping a County of Marin team write a build-ready specification. This is the analyze step.

Read every file and message I have shared in this conversation, including the interview transcript and supporting material. Do not write the specification yet.

Find and list the following. Use a short heading for each.

1. Project problem
2. Goals
3. Users and what they need
4. Current experience
5. Desired experience
6. Workflows
7. Requirements
8. Content
9. Data
10. Integrations and systems
11. Constraints (policies, laws, deadlines, technology limits)
12. Accessibility considerations
13. Security and privacy considerations
14. AI considerations (only if the finished app itself would use AI)
15. Success measures
16. Conflicting information
17. Missing information

Label every item with one of these four evidence statuses:

- Confirmed: the material says so directly. Name the source.
- Inferred: the material reasonably implies it but does not say it.
- Recommended: you or a County of Marin standard suggest it.
- Open question: a decision is still needed.

Rules:

- Never present an inferred or recommended item as confirmed.
- Do not invent facts, users, systems, or requirements.
- Do not assume the finished app uses AI because AI is helping to build it.
- Do not repeat personal information from the material, such as names, emails, phone numbers, addresses, or ID numbers. Refer to people by role. Under security and privacy, list the types of personal information you found, not the values.
- Use plain language.

End with a short list of what you could not find in the material. Then wait for me.

What you get back

A reply with a short heading for each topic, from the project problem to missing information. Every item has one of these labels:

Confirmed
Your material says it directly.
Inferred
Your material implies it but does not say it.
Recommended
The AI tool or a County standard suggests it.
Open question
Someone still needs to decide.

You're ready when

  • You have read every section of the reply.
  • You have corrected anything that was wrong.

Resolve

Answer the questions that change what gets built. Leave the rest to the builder.

What you do

  1. Stay in the same conversation.
  2. Copy the gap prompt, paste it into the message box, and send it.
  3. The tool replies with questions. Type your answers and send them. Ask your project owner if you do not know.
  4. Repeat until the tool says no blocking questions remain.
  5. Leave implementation decisions alone.

Gap prompt

Paste this in the same conversation as the analysis.

You are helping a County of Marin team write a build-ready specification. This is the resolve step.

Using your analysis from this conversation, list every unresolved item that affects what gets built. Sort each one into one of three groups:

- Blocking: the project cannot reasonably proceed without an answer.
- Important: the project can proceed, but the team should make a decision.
- Implementation decision: a developer or coding agent can reasonably decide while building.

For each Blocking and Important item, write:

- a plain-language question a non-technical project owner can answer
- why the answer matters
- your suggested answer, labeled Recommended, if you have one

For Implementation decision items, list them briefly with no questions. Leave them for the builder.

Rules:

- Do not ask technical questions that a developer can decide.
- Do not document every possible choice. Gather enough information to build confidently.
- Do not turn a suggestion into a decision.
- Treat unclear handling of personal information (who sees it, how long it is kept, whether it is shown) as at least Important.

Ask me the Blocking and Important questions one group at a time. When I answer, record each answer as Confirmed and tell me what is still open. Stop when no Blocking items remain and I say the Important items are settled.

What you get back

A reply that sorts what is still open into three groups:

Blocking
The project cannot go ahead without an answer. You get a plain question.
Important
The project can go ahead, but your team should decide. You get a plain question.
Implementation decision
The builder can decide while building. It is listed without a question.

You're ready when

  • The tool says no blocking questions remain.
  • Your team has settled the important ones.

Spec

Write the specification and the project brief.

What you do

  1. Stay in the same conversation.
  2. Copy the spec prompt, paste it into the message box, and send it.
  3. Wait for the reply. Copy each document into a file named SPEC.md or PROJECT-BRIEF.md.
  4. Save a Word copy for your team to review. See "Save a copy for review" below.

Spec prompt

Creates SPEC.md and PROJECT-BRIEF.md.

You are helping a County of Marin team write a build-ready specification. This is the spec step.

Write two documents from everything in this conversation: the shared material, your analysis, and my answers.

Document 1: SPEC.md

Use these sections in this order:

1. Summary (project name, problem, users, desired outcome, project owner, who tests it (UAT) and other stakeholders by role or team, specification status)
2. Platform and delivery (staff or public, security profile: internal, public-web, public-api, authenticated, or custom)
3. Goals
4. Non-goals
5. Users (if the app serves the public, start with the public need)
6. User stories, with IDs US-001, US-002, and so on, in the form "As a (user), I would like (feature) in order to (reason)", one for each user group
7. Workflows
8. Requirements, with IDs REQ-001 and so on. For each: the requirement, priority (P1 must have and critical path, P2 should have, P3 nice to have and can be deferred), evidence status, source, related user story, and acceptance criteria IDs
9. Content (pages, headings, labels, instructions, alerts, empty states, error messages)
10. Data (entities, fields with a label of public, internal, personal, or sensitive, relationships, source systems, formats, APIs, ownership, retention)
11. Integrations
12. Accessibility (target WCAG 2.2 AA; refer to the County of Marin accessibility standard instead of copying it; list only project-specific needs)
13. Security (public and private information, authentication, authorization, roles, sensitive information, how personal information is handled, external APIs, secrets, logging, dependencies; refer to the County of Marin security standard)
14. AI (include only if the finished app itself uses AI)
15. Acceptance criteria, with IDs AC-001 and so on, each testable, in the form "Given (state), when (action), then (result)"
16. Open questions, each marked Blocking, Important, or Implementation decision
17. Sources

Document 2: PROJECT-BRIEF.md

Keep it short, in active voice and plain language. Use these sections: Project, Problem, Why this matters, Users, Experience, Scope, Not included, Key decisions, Deadlines, Key risks and mitigation, Open questions, Success. Leave out Deadlines and Key risks and mitigation when there are none.

Rules:

- Mark every requirement and decision Confirmed, Inferred, Recommended, or Open question.
- Do not turn an inferred or recommended item into a confirmed requirement.
- Do not put real people's personal information in either document. Refer to people by role and make up any example data.
- Do not invent requirements. If something is unknown, put it in Open questions.
- Do not invent security requirements the project or County standards do not support.
- Every requirement must trace to a user story or a stated project need.
- Avoid vague acceptance criteria such as "search works correctly."
- Do not renumber IDs once you assign them.
- Write the Problem in the brief as the underlying goal, not the solution. Back Why this matters with evidence from the material and label it Confirmed or Inferred.

Give me both documents as separate Markdown blocks I can copy into files. If you can create Word (.docx) files, also give me one download for each document. If you cannot, say so.

Save a copy for review

Keep SPEC.md for the coding agent. Also save a Word copy, so your team can read and comment on the spec.

  • The spec prompt asks the tool for Word files. If it gives you downloads, save them.
  • If the tool says it cannot make Word files, send "Show both documents as formatted text, not code blocks." Copy it and paste it into a new Word document. Headings and lists usually carry over.
  • Save the Word files where your team keeps project documents.

What you get back

  • SPEC.md is the full build document, with 17 parts from Summary to Sources.
  • PROJECT-BRIEF.md is a short summary for people.

Source

The spec follows these files:

  • Marin Spec standard
  • Blank templates

You're ready when

  • Both files are saved.
  • A Word copy is saved for your team to review.
  • SPEC.md lists what is still an open question.

Review

Check the spec before anyone builds. A new conversation gives you a fresh check.

What you do

  1. Start a new conversation in your AI tool.
  2. Upload SPEC.md and PROJECT-BRIEF.md.
  3. Copy the review prompt, paste it into the message box, and send it.
  4. The tool replies with a list of issues. Type your answers and send them.
  5. Send "Update both files with these answers." Save the final versions the same way, as Markdown files and Word files.

Review prompt

Checks the spec for gaps and unsupported assumptions.

You are reviewing a County of Marin specification before it goes to a coding agent. This is the review step.

Review the SPEC.md and PROJECT-BRIEF.md I have shared or pasted in this conversation. Be skeptical. If you helped write them in this conversation, review them as if someone else wrote them. Do not rewrite anything yet.

Look for:

- unsupported assumptions
- missing user needs
- missing requirements
- conflicting requirements
- vague requirements
- vague or untestable acceptance criteria
- requirements with no clear user or project need
- unresolved blocking decisions
- real personal information about individuals
- personal-data fields with no decision on who sees them, how long they are kept, or whether they are shown
- accessibility gaps
- security gaps
- data gaps
- integration gaps
- scope creep
- duplicated requirements
- inferred or recommended items that are written as confirmed

List only material issues. For each one give:

- the ID or section
- what is wrong
- why it matters for the build
- a question or a fix to consider

Group issues by severity: Blocking, Important, Minor. Then say whether the spec is ready for a coding agent, and why.

Wait for me to answer. After I resolve the issues, update SPEC.md and PROJECT-BRIEF.md, keep existing IDs, and show me a short list of what changed. Give me the updated documents the same way as before: Markdown blocks, plus Word (.docx) files if you can.

What you get back

  • A list of issues sorted into Blocking, Important, and Minor.
  • A verdict on whether the spec is ready for a coding agent.
  • After you answer, updated files and a short list of what changed.

You're ready when

  • The review shows no blocking issues.
  • You have saved the updated files, including the Word copies.

Build

Give the finished spec to an AI coding agent. It plans first, asks only what it must, then builds.

What you do

  1. Open your coding agent in the project folder. For a new MarinOS app, start from the marin-app-template repository.
  2. Add SPEC.md and PROJECT-BRIEF.md to the folder.
  3. Copy the build prompt, paste it into your agent's message box, and send it.
  4. The agent asks any blocking questions first. Answer them and send your answers.
  5. Read the plan. Tell the agent to go ahead only when it looks right.

Choose a coding agent your team has approved:

  • Claude Code, in a terminal or your code editor
  • OpenAI Codex, or another approved OpenAI coding tool
  • GitHub Copilot in agent mode, in your code editor

Build prompt

Works with any coding agent. Attach SPEC.md first.

You are a coding agent. Build the project described in the attached SPEC.md. This is the build step.

Work in this order:

1. Read the complete specification, including Non-goals and Open questions.
2. Inspect the existing repository.
3. Read the relevant County of Marin standards and the project's own conventions. For a new MarinOS app, start from marin-app-template and follow the marin-app-builder skill.
4. Map each requirement to the existing architecture.
5. List conflicts, missing information, and risky assumptions.
6. Ask me only the blocking questions, and only before you start.
7. Write an implementation plan and show it to me.
8. Implement the plan against the approved specification.
9. Check each acceptance criterion and record the result.
10. Report what changed and which requirements are still incomplete.

Rules:

- Do not reinterpret the project's goals. Raise a conflict or a missing decision instead.
- Do not build anything listed under Non-goals.
- Make implementation decisions yourself. Note the important ones.
- Do not commit, push, or publish anything unless I ask.
- Do not add secrets to the repository.
- Use made-up test data. Never commit real personal information.

What you get back

  • A plan first.
  • Working code.
  • A check of each acceptance criterion.
  • A list of anything left unfinished.

You're ready when

  • Every acceptance criterion is checked.
  • You have read the list of anything left unfinished.
